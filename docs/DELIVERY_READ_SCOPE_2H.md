# 读取依赖也收进范围（2H）

日期：2026-10-31
上一刀：`DELIVERY_WRITE_SCOPE_2G.md`（写入目标三分类）
下一刀预告过的内容：读取侧不对称

---

## 1. 上一刀留下的账

2G 的结尾写着「读取侧仍不对称：写入侧只滤日志，读取侧 `is_framework_read` 滤掉全部 `}`」。
这一轮先把这句话量清楚，再决定动不动。

## 2. 量出来的三件事

### 2.1 库里一条 `}` 边都没有

```
process_reads_cube   5728 条，其中 } 前缀 0 条
process_writes_cube  2752 条，其中 } 前缀 0 条
```

两侧**都**没有系统对象边。所以「读写不对称」不是体现在血缘表里。

### 2.2 不对称在计算检查页

计算检查页的读取依赖是**现场解析源码**得到的（`worksheet()` → `nodes[kind=read]`），
不经过 `process_reads_cube`，也不套 `is_framework_read`。所以它会显示 `}` 读取：

| 抽样 | 读到 `}` cube 的 TI | 最常见目标 |
|---|---:|---|
| 按名字长度取 200 个 | 37（18%） | `}APQ Process Execution Log` 24、`}APQ Settings` 18 |

### 2.3 但真正进入"写入点定义链"的很少

页面「② 此定义链中的读取依赖」只列**某个写入点**的值定义链里实际引用的 CellGet，
不是全部 read 节点。这两个集合差得很远：

```
随机 400 个 TI → 376 个有写入点 / 9721 个写入点
写入点定义链里含 } 读取：53 条（0.55%）
  其中 }APQ Process Execution Log 48、}APQ Dimension Definition 4、}DimensionSecurity 1
不属于任何写入点定义链的 } 读取：137 条（页面本来就不显示，只在 JSON 的 nodes 里）
```

而按名字长度取的前 200 个 TI 里是 **0 条**——分布极不均匀，某些 TI（大量写日志的批处理）
集中出现，多数 TI 一次都没有。

这条比「18% 的 TI 读系统 cube」重要：**收窄的爆炸半径只有 0.55% 的写入点**，
可以放心做，不用像放开 `process_reads_cube`（会多 8834 条边）那样先设计一套图上的收纳方案。

## 3. 决定不做什么

**不放开 `process_reads_cube`。** 理由与 2G 一致：血缘图不追系统/日志读取是**有意**的。
每个 TI 都读 `}APQ Settings`、`}ClientGroups`，画进图里是 8834 条边把业务依赖彻底盖住。

所以只做一件事：**计算检查页列出读取依赖时，系统/日志读取默认收起，并留账可切换。**

## 4. 怎么做的

`store/scope_view.py` 新增 `split_reads()`：给每个写入点分出 `reads_shown` / `reads_hidden`
两个**索引清单**，`read_nodes` 原样保留。

判据不新写：复用 2G 的 `target_kind()` → `plain` / `log` / `system`，日志优先。
文档里不再重复一份清单。

### 4.1 DAG 节点一个不删

这是本轮最关键的取舍。写入点是**清单**，少一条不影响别的；
读取依赖是**推理依据**，砍掉节点会打断 `children` 引用，也会让"这个值怎么算出来的"说不通。

所以：`nodes` 与 `read_nodes` 完整保留，只在渲染层用 `reads_shown` 取数。
导出的 JSON 因此出现一个必须解释的差异——`read_nodes` 是全部、`reads_shown` 是页面那几条。
**这个差异写进了导出正文**，不是留给读者自己发现：

> JSON 里 writes[].read_nodes 仍是完整定义链（节点不裁剪，否则推不出结论）；同一写入点的 reads_shown 才是页面上那几条。

### 4.2 全部读取都被收走时，不能说"没有来源"

页面原来在读取依赖为空时写「没有可确认的直接读取依赖」，并补一句"不据此判定无来源"。
一旦收窄，这个分支会变成假话：读取明明是有的，只是被范围收走了。

现在分成两句：

- 有可见读取 → 正常列；
- 全部被收走 → 「此写入点的读取依赖全部落在日志或系统立方体上，已按页面范围收起；切到全量可逐条核对。」

概览条（读取依赖那一格）同步改成「已收起的系统读取」，不写"常量 / 参数"。

### 4.3 顺手补掉的一个分支缺陷

`scope_lines()` 原来在 `not info['hidden']` 时提前返回「本次没有需要隐藏的记录」。
加入读取维度后，这个提前返回会在「写入点一条没少、读取依赖少了」时
**先说没有隐藏、再什么也不解释**。

测试 `test_export_says_where_the_two_views_differ` 抓到，改为两个分支分开写：

- 写入点有隐藏 → 「另有 N 条记录未包含在本文件内」+ 构成 + 指向；
- 写入点没隐藏、读取有隐藏 → 「没有写入点因范围被排除」+ 读取那一段。

两句都写，因为这两件事的读者动作完全不同：前者去列表里找短项，后者去定义链里找。

## 5. 前端变化

计算检查页「② 此定义链中的读取依赖」多一条琥珀色提示（`.scope-inline`）：

> 另有 1 条读取依赖未显示（1 条指向系统立方体）：}APQ Settings。隐藏不等于这个值没有来源。
> 把这 1 条一起看 →

链接带 `system=1`，与写入点共用同一个开关——**不给第二个参数**，
否则两个范围状态会各自漂移。

## 6. 验证

- 新增 `tests/test_read_scope.py` 5 条：收起并报名字、全部收起不说假话、`system=1` 拿回且不再提示、导出正文写清 `read_nodes` 与 `reads_shown` 的关系、全量时 `reads_hidden=0`。
- 两处精确 `scope_view` 断言按新字段更新（`reads_hidden` / `reads_total`）。
- 全量 **1260 passed**（1255 + 5）。
- `data/`、`collections/`、`cache/` 零改动，真实库全程只读。

## 7. 没做的与风险

1. **暗色主题没有截图确认**——样式已写（`.scope-inline`），环境里没有浏览器。
2. **真实命中率低**（0.55% 的写入点）。功能正确，但多数页面看不出差别；
   要说这轮"更准了"，只在那些写日志的批处理 TI 上成立。
3. **137 条游离的 `}` 读取**：不属于任何写入点定义链，页面从来不显示，
   只在 JSON `nodes` 里。是否要在 JSON 里标出它们（`reads_shown` 之外的读取），
   留到需要时再说——现在标了也没有页面消费。
4. **`process_reads_cube` 与计算页的读取口径仍不一致**（差数据源声明、bedrock；
   实测"只在计算页"的业务读取 0 个，方向单边）。这一刀没动血缘表。
