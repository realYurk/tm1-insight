# 真实规模下的可读性

本文件记录 Module Dossier 在**有 Rule 源码**的真实模块上的表现，以及为什么
档案层要主动截断与合并。合成场景（`EXAMPLE_MODULE.md`）只有两条 Rule，看不出
这些问题。

## 1. 样本

仓库内两份离线库：

| 库 | Cube | 有 Rule 源码 | 用途 |
| --- | --- | --- | --- |
| `data/db` | 3660 | 0（旧格式导出包） | 验证「未记录」与「确实没有」的区分 |
| `data/demo` | 3338 | 1339（最大 616 KB） | 验证真实 Rule 下的可读性 |

取 `data/demo` 上一个「1 个装载 TI → 1 个 436 KB Rule 的 Cube」的模块，默认预算。

## 2. 第一版的结果：数字对，读不了

| 项 | 值 |
| --- | --- |
| `Module.md` | 335 010 字符 |
| `Questions.md` | 174 425 字符 |
| 缺口 | 660 项 |
| 其中 `RULE_PARTIAL` | 415 |
| 其中 `FEEDER_PARTIAL` | 199 |

章节构成说明了问题在哪：

| 章节 | 字符 | 占比 |
| --- | --- | --- |
| 5. Rule 与 Feeder | 186 837 | 56% |
| 7. 验证缺口 | 105 934 | 32% |
| 4. 目标结果 | 24 217 | 7% |
| 2. 数据模型 | 8 182 | 2% |

两条根因，都不是「引擎算错了」：

**根因一：缺口的原因带着行号，聚合键被行号打断。**
`RULE_PARTIAL` 的 `reason` 是 `第 9–15 行：AREA_MEMBER_OWNERSHIP_UNKNOWN: …`。
同一句原因在 60 条 Rule 上出现，行号不同就成了 60 个不同的键，去重逻辑一次都没命中。
614 行重复把 12 类真实缺口淹掉了。

**根因二：Rule 表的每一格都是完整原文。**
Rule 区域是一个成员集合的字面列表，一条可以三四百字符；表达式最长 9118 字符。
84 条全部完整渲染，等于把 Rule 源码倒进正文——正是任务书里明确不要的做法
（「不要把完整源码、日志及大规模 JSON 直接塞进 Markdown 正文」）。

## 3. 改法

三层，都在呈现侧，不改任何事实：

**（一）行号移出原因，成为受影响位置。**
`gap()` 把 `第 X–Y 行：` 前缀拆进 `locations`，`reason` 只留原因本身，`(对象, 环节,
代码, 原因)` 作合并键，`count` 记录合并了几处。逐条记录一条不丢，全部进
`verification_gap_entries`。

**（二）明细分层。**
Rule 表每 Cube 前 25 条、Feeder 前 20 条；区域列截 96 字符、表达式列截 240 字符、
引用最多 4 个。截断在文档里明说，完整值留在 `Module.json`。

**（三）预算兜底。**
`Module.md` 超过 120 000 字符时，用更少的 Rule 行重新渲染一次（25 → 8 → 6），
而不是把表格从中间切掉。半张表读起来像完整的，比没有更糟。

## 4. 改后

| 项 | 改前 | 改后 |
| --- | --- | --- |
| `Module.md` | 335 010 | **75 239**（−78%） |
| 其中 Rule 与 Feeder | 186 837 | 15 126 |
| 其中验证缺口 | 105 934 | 17 875 |
| `Questions.md` | 174 425 | 29 832 |
| 缺口行数 | 660 | 86 组 |
| 缺口实际处数 | 660（去重后，少算 375 处） | **1035**（逐行，全记） |
| 生成耗时 | 2.5 s | 2.5 s |

注意第三行：**合并之后记录的缺口反而更多了**。旧的去重键 `(对象, 代码, 原因含行号)`
把同一行的多个原因当成重复丢掉；现在每个原因各自成组、各自带位置，1035 处一处不少。
「读起来更短」和「信息更少」是两件事。

## 5. 改后读者看到什么

第 5 节末尾：

```
Rule 未确认项（同一原因合并计数）：

- AREA_COORDINATE_UNCONFIRMED: 区域坐标仍有未确认项（81 条）
- AREA_MEMBER_OWNERSHIP_UNKNOWN: 裸成员/集合缺少成员归属索引；不能按 Cube 维度顺序推断（81 条）
- EXPRESSION_SEMANTICS_NOT_RECONSTRUCTED: 仅保留表达式结构和引用，未还原完整计算语义（71 条）
- FUNCTION_SEMANTICS_NOT_RECONSTRUCTED: ATTRS（60 条）
- DB_COORDINATE_DYNAMIC: DB 坐标表达式尚未还原（50 条）
```

第 7 节表头：

```
同一对象上的同一原因合并为一行：**86 组 / 1035 处**。`受影响` 只列前 6 个位置，
逐条记录见 Module.json 的 verification_gap_entries。
```

一行示例：

```
| GAP-001 | BP Stock Assumption | rules | RULE_PARTIAL |
  第 9–15 行、第 18–24 行、第 33–37 行、第 39–43 行、第 46–50 行、第 66–70 行 等 40 处 |
  AREA_MEMBER_OWNERSHIP_UNKNOWN: 裸成员/集合缺少成员归属索引；不能按 Cube 维度顺序推断 |
  该条 Rule 的完整区域或表达式未确认 | 核对该行源码与成员索引 |
```

## 6. 仍然存在的量

75 K 字符对一个 84 条 Rule 的模块是合理的，但不是「小」：第 4 节 24 K（20 处写入
详情，每处含坐标映射表）和第 7 节 18 K（86 组）是主要剩余。两者都是核心内容，
再压就要牺牲可核对性。

若要更短，正确的做法是缩小分析范围（少纳一个 Cube、把写入点预算从 20 降到 10），
而不是继续削减呈现——那会把「这里为什么这么写」变成「不知道，去看 JSON」。
