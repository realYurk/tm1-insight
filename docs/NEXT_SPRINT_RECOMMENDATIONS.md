# NEXT_SPRINT_RECOMMENDATIONS

> 前提：本轮只做「让已有功能正确、可读、可信」，未扩张产品范围。
> 以下建议全部基于**当前代码已具备的能力**，不依赖新引擎。

## 优先级 1：设计草稿 → 真实代码模板

现状：`DraftCube` 已能按序声明维度并保存进工作区，但模板页只接受真实 Cube（`workspace-codegen.js` 明确拒绝草稿作为来源/目标）。

价值：这是从「理解现有系统」走向「设计新系统」的第一步，也是用户明确关注的长期方向。

做法：

- 模板页允许选择工作区中的草稿作为**目标**，并在 UI 中标明「目标尚未部署」。
- 生成代码时，维度顺序取自草稿声明；成员映射仍由用户人工配置。
- 生成结果标注 `DESIGN_DRAFT` 来源，不得写成模型事实。

验收：

- 草稿 → 模板 → 生成结果中维度顺序与草稿一致。
- 草稿不出现在血缘图的计算关系中。
- 与真实 Cube 的项目在视觉与导出中可区分。

## 优先级 2：Rule 级上游下钻

现状：图上 Rule 边是 Cube 级（`RULE_REFERENCE`），逐条 Rule 的表达式、行号、引用只在右侧面板可见；图上无法从某条目标区域继续向上。

价值：用户分析一条链路时最常问的是「这个指标由哪条 Rule、引用哪个 Cube 的哪个区域算出来」。

做法：

- 在右侧 Rule 列表中为每条 Rule 提供「在图展开该 Rule 的上游」。
- 生成的是**子图请求**（复用现有 `/api/workbench/graph` + `relation_types`），不新增查询引擎。
- 展开后的边必须携带 `line_start` 与目标区域，点开即定位源码。

验收：

- 从 `Planning PnL` 的某条 Rule 展开后，图上出现其 `DB()` 引用 Cube。
- 点击该边能定位到源码行号。
- 无法确定目标区域时显示「待确认」，不生成箭头。

## 优先级 3：外部数据源节点

现状：TI 详情只显示数据源类型（`VIEW` / `ASCII` / `ODBC`）与「字段结构未取得」，明确不打开文件、不执行 SQL。

价值：`CSV → TI → Cube` 是用户长期关注的入口，但必须以「静态声明」为边界。

做法：

- 图查询中把已声明的数据源呈现为**独立节点类型**（`external_source`），边上标注 `DECLARED_DATASOURCE`。
- 字段结构保持 `UNKNOWN`，除非用户在本地主动提供列名与类型。
- ODBC 只显示「声明存在」，隐藏连接串、账号与服务地址。

验收：

- 外部源节点与 Cube 节点视觉可分。
- 未提供 Schema 时不显示任何字段名。
- 导出内容不含连接信息。

## 优先级 4：工作区作为工程资产

现状：工作区已保存分组、备注、草稿、MDX 与 `template_ref`（当前只有 `cube-data-transfer` 一个取值）。

价值：把「这一次的分析」沉淀为「下一次可复用的资产」。

做法：

- 工作区导出增加 `asset` 段：可复用的模式名、适用的处理类型、验证要点。
- `template_ref` 扩展为多值清单，指向现有模板而非新模板引擎。
- 资产文件仍保存在用户目录，不进入默认分发包。

验收：

- 导出的资产可在另一工作区导入并保留分组与备注。
- 资产不包含企业源码正文。

## 本轮明确不做

- 完整 Java / Python 逆向工程
- 通用分摊引擎重写（现有分摊模块保持现状）
- 在线 TM1 IDE、企业服务器操作
- 内置 AI / 云端模型调用 / 遥测
- 多租户、微服务拆分、低代码全栈生成器

## 判断依据

当前的短板不是「功能数量」，而是：

1. 右侧详情与图形之间还差一步「按 Rule 下钻」。
2. 设计与实现的闭环缺「草稿进入模板」。
3. 资产沉淀有了容器（工作区），缺可复用语义。

这三件事都能在现有 API 与组件上完成，不需要新引擎，也不会破坏已验收的行为。
