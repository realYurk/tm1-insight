# 分摊框架评估（allocation_framework_assessment.md）

> 对应交付：`allocation_engine.py`（计算内核）+ `/allocation` 页面 + 18 项测试。
> 评估对象：旧 BP TI 分摊体系 vs 本轮可配置分摊原型。评估只基于本地离线 Snapshot 中可核对的源码事实。

## 一、旧系统（BP TI 分摊）已经证实了什么

以下每条都来自已采集的 TI 源码静态证据（写入索引、调用索引、源码哈希），不是名称推断。

| 旧系统已证实的能力 | 证据来源 | 对新框架的含义 |
|---|---|---|
| TI 批量读取 View 数据源并逐行写入目标 Cube | VIEW_DATASOURCE 绑定 + Data 行写入坐标 | 新框架的"源数据 / 目标数据"表就是这条链路的抽象 |
| 多维目标坐标逐维度赋值（固定成员 + 行变量 + 参数） | write_explanations 的 target_coordinates | 新框架用 allocation_dimensions 显式声明目标维度 |
| 条件写入（IF 分支控制是否落账） | 源码中的条件语句与 conditions 记录 | 新框架目前不做条件写入，见"还不能证明" |
| CellIncrementN 累加语义 | 写入模式 INCREMENT 计数 | 新框架 write_policy=increment 对应此语义（仅记录，不执行） |
| 按基地 / 公司等维度分组隔离执行 | 源码中的固定筛选切面 | 新框架 group_dimensions 强制组内分摊，跨组不泄漏（已测试） |
| 驱动因子来自假设 Cube（如 BP PnL Assumption） | RULE_DB_REFERENCE / CUBE_READ 证据 | 新框架 driver_field 显式声明；因子聚合方式为组内求和 |
| Caller / RushTI 编排调用 | PROCESS_CALL 关系与调用索引 | 新框架不涉及编排；执行顺序由调用方负责 |

## 二、新框架主动设计了什么

| 设计点 | 决策 | 理由 |
|---|---|---|
| 配置驱动 | 全部参数（分组、目标、驱动、策略）来自一份 JSON config | 分摊逻辑与 TM1 执行解耦，可先在合成数据上验证 |
| 组隔离 | group_dimensions 组成组键，组间金额与因子严格不交叉 | 复刻旧系统按基地分摊的语义并有测试覆盖 |
| 比例计算 | 组内按驱动因子占比分配，Decimal 精确计算 | 避免 float 误差；比例随结果输出供审计 |
| 零分母 | 整组跳过并记录异常，不静默丢弃 | 分母为零时比例无定义，必须人工介入 |
| 负驱动 | 合计为负整组跳过；个别为负仍按比例（负数）分配并提示 | 负比例业务含义未知，交给人工确认 |
| 缺失驱动 | 记 0 分摊 + 异常提示 | 不中断整组计算，但不无声吞掉 |
| 尾差处理 | 逐行 ROUND_HALF_UP，最后一行吸收尾差 | 组内总额绝对守恒（已测试 100→33.33/33.33/33.34） |
| 守恒对账 | reconcile() 按组与总体校验源合计=分配合计 | 分摊正确性的最低底线 |
| 幂等重跑 | 同一 config 哈希一致、结果一致；累加语义由调用方对基准负责 | 内核每次从源值完整重算，重复执行不会二次累加 |
| 方案资产 | 保存 / 加载 / 导出 / 导入 JSON，存独立目录 | 方案可复用、可版本管理；不混入模型数据 |
| 安全边界 | 不连接 TM1 Server、不执行 TI、不写 DuckDB / Cube | 原型阶段只允许合成数据；真实 Cube 执行需另行授权与实现 |

## 三、还不能证明什么（当前边界）

| 缺口 | 说明 |
|---|---|
| 完整旧分摊执行顺序 | Chore / Caller 的实际执行顺序未被静态分析证明，新框架不声称复刻它 |
| 部分源值变量绑定 | 旧 TI 中部分 Data 行变量来源仍 UNKNOWN（动态读取目标未解析） |
| 动态目标成员 | 旧写入坐标中 UNRESOLVED 类型的动态成员，新框架的 allocation_dimensions 不覆盖 |
| 全部 Rule 运行语义 | 目标 Cube 上的 Rule 在写入后如何二次计算，未求值 |
| 新旧结果等价 | 未在真实模型上执行对比，第一版禁止；等价性需要未来在隔离环境验证 |
| 条件写入 | 旧系统的 IF 分支控制写入，新框架尚无对应配置项 |
| 因子来源连接 | 新框架因子为手工输入；未与假设 Cube 的读取打通 |

## 四、结论

新框架完成了"分摊算法内核 + 配置 + 对账 + 方案资产"的最小闭环，且行为全部有测试锚定。
它目前是**通用执行原型**，不是旧 BP 分摊的等价替换；下一步最高价值是把"驱动因子来源"接到已有
Cube 读取索引（仍然只读快照），并补齐条件写入配置。
