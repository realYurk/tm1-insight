# NEXT SPRINT — 建议

> 依据：本轮实际完成度与已知缺口，不写未实现的能力。

## 推荐：A. 继续增强工程资产（但收窄到三件事）

理由：3.0 已经把「设计 → 提炼 → 绑定 → 生成」跑通，但资产本身还很薄——没有版本历史、没有编辑、验证契约没有 UI。
现在转去做分摊（B）会让资产变成一次性产物，无法沉淀。

### A1. Blueprint 版本与差异

- `version` 已存在但只手动递增；需要「另存为新版本」与两版差异（角色、映射、策略）。
- 验收：同一 Blueprint 两个版本可并列查看差异；项目实例记录使用的版本，仍可重新生成旧版。

### A2. 资产库内编辑（角色改名 / 删角色 / 改默认值）

- 当前只能新建、绑定、删除、导入；要支持在资产页修改角色描述与默认值（不动维度顺序结构）。
- 验收：改名后已存在的项目实例仍能打开，并提示「基于旧版绑定」；重新生成时给出明确差异。

### A3. 验证契约落地

- `VerificationContract` 只有数据模型，没有 UI，也没有和生成结果联动。
- 需要：在生成后按契约逐条给出 `passed / blocked / manual`，并在项目详情展示依据。
- 验收：删除一条必需映射时，契约中对应项变红且阻断生成；只有静态可判定的项才显示"通过"。

## 次选：D. Portable 与交付质量

- 干净 Windows 环境验证、安装/升级说明、资产备份与恢复入口。
- 若近期要对外分发，这一项优先级会超过 A。

## 暂不建议：B. 配置驱动分摊组件

分摊组件需要先有「可复用的验证契约 + 版本化资产」，否则每套分摊方案都是一次性脚本。
建议在 A3 完成后启动，并用本轮的 Blueprint 机制承载「分摊步骤」这类复合资产。

届时需要确认的扩展点（本轮已预留位置，未实现）：

- `Blueprint.mappings` 目前是单层；分摊需要 `StepChain`（多步、带依赖）；
- `ProjectInstance` 需要记录「多关系」而非单一关系；
- 验证契约需要支持「守恒 / 对账」类跨行断言（现有 8 种 kind 不含）。

## 明确不做（与任务书一致）

- Java/Python 逆向引擎、Spring Cloud 低代码平台、MySQL 在线建模
- 自动部署到 TM1、读取业务数据、执行 TI
- 内置 AI、多租户、联网激活
